# Security Policy

## Supported versions

| Version | Supported | Notes |
|---------|-----------|-------|
| 1.0.x (`main`) | ✅ | Receives security fixes |
| < 1.0 | ❌ | Pre-release, please upgrade |

## Reporting a vulnerability

**Please do not open a public GitHub issue for security problems.**

1. Report privately through **GitHub Security Advisories**: go to the repository's **Security** tab and click **Report a vulnerability**. This creates a private advisory that only the maintainers can see.
2. Include:
   - A description of the vulnerability and its impact
   - Steps to reproduce, or a proof of concept (a minimal `curl` sequence is ideal)
   - The affected version or commit SHA
   - Any suggested fix (optional)
3. Please test only against **your own local instance**. Do not test against deployments you don't own, and do not access other users' data.

### What to expect

| Stage | Target time |
|-------|-------------|
| Acknowledgement | within **3 working days** |
| Triage and severity (CVSS v3.1) | within **7 working days** |
| Fix for Critical / High | within **14 days** of triage |
| Fix for Medium / Low | next scheduled release (≤ 90 days) |
| Public disclosure | coordinated with the reporter after a fix is released |

Reporters are credited in the advisory and release notes unless they ask to stay anonymous.

### Safe harbour
Research done in good faith, within this policy, is welcome. We will not pursue legal action against it. Good faith means:
- Avoiding privacy violations, data destruction and service disruption
- Only interacting with accounts you own
- Giving us reasonable time to fix the issue before disclosure

## Scope

**In scope:** source code in this repository, the Docker image built from it, and the CI workflow.

**Out of scope:** findings that need a compromised host or a malicious administrator. Missing best-practice headers on non-production `/docs`. Denial of service through volumetric traffic. Reports generated by automated scanners with no demonstrated impact.

## Security update policy

- Dependencies are monitored weekly by **Dependabot** (pip, GitHub Actions, Docker), with a 7-day cooldown before new releases are adopted.
- Every PR must pass the **Security Gate**: Semgrep SAST, Trivy image scan and pip-audit. HIGH and CRITICAL findings block the merge.
- Security fixes are released as patch versions (`1.0.x`) and announced in a GitHub Security Advisory.
- If a fix needs a configuration change (for example rotating `JWT_SECRET_KEY`), the advisory gives step-by-step instructions.

## Known mitigations and hardening guidance

| Risk | Built-in mitigation | Operator action required |
|------|---------------------|--------------------------|
| Weak or default JWT secret | App refuses to start if `JWT_SECRET_KEY` is missing, shorter than 32 characters or a placeholder | Generate with `secrets.token_urlsafe(48)` and store it in a secrets manager |
| Token theft | httpOnly + Secure + SameSite=Strict cookies, 15-min access tokens, refresh rotation with reuse detection | Serve **only** over HTTPS and keep `COOKIE_SECURE=true` |
| Brute force | 5 req/min on auth endpoints | Use Redis storage when running more than one replica. Alert on `login_failed` spikes. |
| Cross-origin abuse | Explicit CORS allow-list, `*` rejected | Set `CORS_ORIGINS` to your exact frontend origin(s) |
| Host header attacks | `TrustedHostMiddleware` in production | Set `ALLOWED_HOSTS` |
| Information leakage | Docs disabled in production, generic errors, no `Server` header | Keep `ENVIRONMENT=production` in deployed environments |
| Secret compromise | `token_version` revocation | If `JWT_SECRET_KEY` leaks, rotate it. All sessions end immediately. |
